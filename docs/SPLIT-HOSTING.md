# Онлайн-статус и отдельные хосты фронта/бэка

## Как работает присутствие

- Открытый сайт получает состояние Django примерно раз в 5 секунд. Такой запрос подтверждает активность текущей браузерной сессии; время в БД обновляется не чаще раза в 20 секунд.
- Если подтверждений нет 90 секунд, сессия перестаёт считаться подключённой. С учётом записи времени и следующего опроса друга индикатор обычно гаснет через 70–95 секунд после закрытия последней вкладки или потери связи. При сне устройства фоновые таймеры могут быть остановлены — тогда оно тоже станет оффлайн.
- При обычном выходе из аккаунта сервер сразу удаляет присутствие этой сессии. Друг увидит изменение при следующем опросе, обычно в течение 5 секунд.
- Вкладки одного браузера используют общую сессию. Закрытие одной вкладки не выключает остальные. Разные браузеры/устройства хранят отдельные записи; достаточно одной активной сессии.
- После возврата на вкладку или восстановления интернета клиент сразу повторяет запрос. Точное время последнего посещения и идентификаторы сессий другим пользователям не выдаются. Заблокированному собеседнику показывается оффлайн.
- **Профиль → Редактировать → Отображение статуса:** «Автоматически» показывает подключение, «Невидимый» всегда показывает оффлайн, «В игре (вручную)» действует только пока есть подключение. Старые ручные настройки сохранены. Автоматического определения запущенной игры нет.

Данные `PresenceSession` хранятся в общей БД Django, поэтому процесс API можно перезапустить или запустить несколько рабочих процессов. Память одного процесса не является источником статуса. Все процессы одного магазина должны использовать одну БД и один `DJANGO_SECRET_KEY`. Старые записи старше суток очищаются при обновлении присутствия. WebSocket и Redis для текущего учебного размера проекта не нужны.

## Локально

Ничего менять в адресах не требуется:

```powershell
# Из корня проекта, после обновления кода:
.\.venv\Scripts\python.exe backend/manage.py migrate

# Терминал 1:
cd backend
..\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000

# Терминал 2, из корня:
cd frontend
npm.cmd run dev
```

По умолчанию `VITE_API_BASE_URL=/api/v1/`. Vite проксирует `/api` и `/media` на порт 8000. Для другого адреса локального бэка задайте `API_PROXY_TARGET` до запуска Vite. Эта переменная работает только для сервера разработки, а не внутри готового `dist`.

## Вариант 1: два хоста, прокси на стороне фронта

Это предпочтительный вариант, особенно если хостинги дают несвязанные домены. Файлы React живут на первом хосте, Django — на втором. На хостинге фронта настройте внутреннее проксирование, не HTTP-перенаправление браузера:

| Запрос к фронту | Куда проксировать |
| --- | --- |
| `/api/*` | `https://your-backend.example/api/*` |
| `/media/*` | `https://your-backend.example/media/*` |
| Остальные страницы | Файлы `dist`, отсутствующий путь → `index.html` |

Прокси должен сохранять метод, тело, Cookie/Set-Cookie, Origin и пользовательские заголовки, передавать правильный Host бэка и не кешировать `/api/*`. Если хостинг меняет Domain у cookies, они должны оставаться привязаны к домену фронта; Django по умолчанию не задаёт Domain. API и media необходимо обрабатывать раньше SPA fallback.

Фронт перед сборкой:

```dotenv
VITE_API_BASE_URL=/api/v1/
```

Бэк, пример для HTTPS:

```dotenv
DJANGO_DEBUG=0
DJANGO_ALLOWED_HOSTS=your-backend.example
CSRF_TRUSTED_ORIGINS=https://your-frontend.example,https://your-backend.example
CORS_ALLOWED_ORIGINS=https://your-frontend.example
SESSION_COOKIE_SAMESITE=Lax
```

Задайте свой `DJANGO_SECRET_KEY` в секретах хостинга. В `DJANGO_ALLOWED_HOSTS` добавьте также домен фронта, если ваш прокси сохраняет его в Host. Для браузера API остаётся на адресе фронта, хотя физически работает на другом сервере; сторонние cookies не требуются.

## Вариант 2: прямое обращение к отдельному API

Удобно при своих поддоменах, например `store.example.com` и `api.example.com`, оба по HTTPS. Фронт перед `npm run build`:

```dotenv
VITE_API_BASE_URL=https://api.example.com/api/v1/
```

Бэк:

```dotenv
DJANGO_DEBUG=0
DJANGO_ALLOWED_HOSTS=api.example.com
CORS_ALLOWED_ORIGINS=https://store.example.com
CSRF_TRUSTED_ORIGINS=https://store.example.com,https://api.example.com
SESSION_COOKIE_SAMESITE=Lax
```

Клиент отправляет запросы с `credentials: include`, получает CSRF-токен в ответе API и не пытается читать cookie другого домена. CORS разрешает credentials и заголовки CSRF, `Idempotency-Key`, `X-Store-User` только для перечисленных origin. Произвольный внешний адрес API не принимает. Обложки, галереи и аватары из `/media/`, а также ZIP мастерской используют адрес бэка; встроенные `/art/` остаются на фронте.

При несвязанных доменах cookie-сессии могут потребовать `SESSION_COOKIE_SAMESITE=None` и HTTPS (`DJANGO_DEBUG=0`). Однако браузер всё равно может заблокировать сторонние cookies. Эта настройка не гарантирует работу на любых доменах: используйте прокси из варианта 1 либо собственные поддомены одного сайта. Не решайте проблему выключением CSRF или разрешением всех origin.

Переменные `VITE_*` входят в клиентскую сборку и публичны: в них нельзя класть секреты. После смены `VITE_API_BASE_URL` пересоберите и заново разместите `dist`. После изменения настроек Django перезапустите API. По HTTPS нельзя указывать HTTP-адрес бэка.

## Что ещё нужно хостингу

Миграции запускаются на бэкенде: `python manage.py migrate`. Статику админки собирает `python manage.py collectstatic --noinput`. `runserver` не используется как production-сервер. При `DJANGO_DEBUG=0` раздачу `/media/` должен обеспечивать хостинг/веб-сервер или объектное хранилище; Django development-раздача отключена. База, `media` и `private_uploads` должны находиться в постоянном хранилище. Каталог `private_uploads` не должен иметь публичного URL.

Если бесплатный хостинг усыпляет бэкенд, при пробуждении возможна задержка входа и обновления статуса. Онлайн здесь означает открытый сайт с живой сессией, а не присутствие человека за компьютером.

## Проверка перед показом

1. Откройте два аккаунта в обычном и приватном окне/разных браузерах. В обоих выберите «Автоматически», добавьте друг друга в друзья.
2. В друзьях, чате и профиле должны появиться зелёный индикатор и «В сети».
3. Выйдите из одного аккаунта — второй увидит оффлайн при следующем опросе. Зайдите снова — онлайн вернётся.
4. Закройте все вкладки одного аккаунта без выхода; индикатор погаснет после тайм-аута. Если оставить другое устройство открытым, пользователь останется онлайн.
5. Включите «Невидимый»: другой аккаунт должен видеть оффлайн. Проверьте обычный вход, пополнение и изображение игры на адресах хостинга.

Автотесты: стандартные серверные/клиентские проверки из README и `npm run test:integration:split` из `frontend` с переменной `PYTHON`. Последняя команда прогоняет настоящие React и Django с разными origin на отдельной временной БД. Публичный хостинг без выбранных адресов этой командой не разворачивается.

Проверено 24 сентября 2026: 175 серверных тестов (170 прошли, 5 проверок SQL Server пропущены на SQLite), 71 клиентский тест, ESLint, production-сборка и обе сквозные конфигурации API. В настоящем браузере дополнительно проверены вход через CORS и автоматические переходы друга «Не в сети → В сети → Не в сети» без перезагрузки страницы. SQL Server, Docker и публичный хостинг в этой проверке не запускались.
